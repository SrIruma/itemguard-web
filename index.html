ItemGuard

Track, find and protect the valuable items you hand out. A staff tool for Paper 1.21+.

Paper 1.21+ Java 21 SQLite Folia ready

ItemGuard is for servers that give players items worth real money — crate rewards, ranks, custom gear. Once an item is tracked, it gets a unique ID, a record of everywhere it's been, and a set of flags that decide what can happen to it. If something goes wrong, you can trace it, find it and get it back.

It's a staff tool, so nothing is switched on by default. Operators don't automatically get access — you choose who can touch tracked items and what they can do with them.

What you get

  • Unique IDs — every item gets an ID like IG-7-a4f2 that never changes.
  • A full history — a running log of every move: drops, pickups, container transfers, deaths.
  • 33 flags — decide exactly what an item can do. Be dropped? Hopper-transferred? Crafted? Burned?
  • Locked ownership — the owner is set when the item is issued and doesn't change afterwards.
  • Recovery — find a missing item, teleport to it, seize it, or rebuild it from its stored copy.
  • SQLite only — one local file. No database server to run or connect to.
  • Addons — hook ItemGuard into other plugins through the API. SmartSpawner ships as a bridge.

Installation

What you need

ServerPaper 1.21 or newer (Folia works too)
Java21+
DatabaseSQLite — bundled, nothing to install

Setup

  1. Drop ItemGuard.jar into your plugins/ folder.
  2. Got addons? Put their JARs in plugins/ItemGuard/addons/.
  3. Start the server. ItemGuard creates plugins/ItemGuard/ with the config, the language files and itemguard.db.
  4. Give your staff the permissions they need — see Permissions.
Where things go. The plugin JAR sits in plugins/. Addons go in plugins/ItemGuard/addons/. The config, translations and database all live in plugins/ItemGuard/.

Permissions

Nothing is granted by default — not even to operators. Give one person itemguard.admin and they get the whole plugin, or hand out the individual nodes instead.

NodeWhat it allows
itemguard.adminEverything in ItemGuard, and nothing outside it.
itemguard.giveHand out tracked items with /ig give.
itemguard.blueprintCreate, overwrite, hand back and delete blueprints.
itemguard.item.readLook items up: /ig item find, tp, list, info.
itemguard.item.writeMove items around: /ig item recover, seize, unseize.
itemguard.reloadReload the config and translations.
Want operators to have everything? Set permissions.ops-are-admins: true in config.yml. It's read once at startup, so a reload won't change it — you'll need a restart.

Protection flags

Every tracked item has 33 flags. Each one is named after the action it controls, not the protection — droppable: false means "this item can't be dropped". They're grouped into five families.

Move

FlagDefaultWhat it controls
droppablenobodyWhether the owner can drop the item on the ground.
pickupableowner onlyWhether the owner can pick the item back up off the ground.
movableeveryoneWhether a slot can be rearranged inside one inventory.
stowableeveryoneWhether the item can go into a container.
retrievableeveryoneWhether the item can be taken back out of a container.
swappableeveryoneWhether the item can be swapped between hands.
drop-on-deathnobodyWhether the item drops to the ground when its owner dies.

dispenser-takenobodyWhether a dispenser can pull the item out.

smithablenobodyWhether the item can be used at a smithing table.

weareveryoneWhether the item can lose durability.

repairableeveryoneWhether the item can be repaired or renamed on an anvil.

World

FlagDefaultWhat it controls

burnablenobodyWhether the item can burn in fire or lava.

piston-movablenobodyWhether a piston can move the placed block.

weather-proofnobodyWhether lightning or rain can reach the item.

Admin

FlagDefaultWhat it controls
recoverableeveryoneWhether the item can be rebuilt from its stored copy.

No flags match that filter.

What happens when something is refused. ItemGuard either cancels the event, undoes it after the fact, or rebuilds the item. If a refused action would have destroyed the item, it's queued for redelivery instead — so the owner gets it back rather than losing it to a rule that was supposed to protect them.

Placeholders

Item names and lore can contain tokens that get filled in when an item is issued. Use them in a blueprint to stamp each copy with its own ID, owner, date and flags.

They resolve once, at issue. A token is filled against the item being created, never against the blueprint. So a sword whose lore says Owned by {ig.owner} records the buyer's name the moment it's delivered — and blueprint get still hands back the recipe with the token untouched.

Two syntaxes

Either form works and means the same thing. Only the ig. and itemguard. prefixes are touched, so someone else's {owner} is left alone. The braced form is the one to prefer, because dots survive in keys like drop-on-death.

BracedPercent
{ig.owner}%ig_owner%
{ig.flag:droppable}%ig_flag_droppable%
{ig.flag:drop-on-death}%ig_flag_drop_on_death%
{itemguard.version}%itemguard_version%

An unknown key isn't blanked — it's left exactly as you wrote it, so a typo shows up on blueprint get instead of quietly disappearing.

{ig.material}The base item type, e.g. DIAMOND_PICKAXE.

Addon API

Getting started

Write a bridge between ItemGuard and another plugin. The API is free and MIT-licensed.

It's one interface and one service file. There's no registration call and you don't depend on ItemGuard's classes — implement ItemGuardIntegration, list your class in META-INF/services/, and ItemGuard loads it on startup.

Add the dependency

Pull in the API as provided, so it's never bundled into your JAR.

<dependency>
  <groupId>dev.mugi</groupId>
  <artifactId>itemguard-api</artifactId>
  <version>1.0.0</version>
  <scope>provided</scope>
</dependency>

Register the bridge

Create META-INF/services/dev.mugi.itemguard.addon.ItemGuardIntegration in your JAR and put the fully qualified name of your class in it:

com.example.MyBridge

Addon API

Rules & example

Worth keeping in mind

  • Don't throw. Every call is wrapped. If your code throws, the bridge gets marked unavailable and you've already eaten the block event that triggered it.
  • Don't compile against the other plugin. Look it up by name at runtime and load its classes from its own loader, so your bridge loads whether or not that plugin is installed.
  • Stay fast. ownsBlock runs on block events — resolve your reflection once in isAvailable and cache it.
  • Return false when you're not sure. Claiming a block you don't own means staff can't find or seize it later.

Full example

public final class MyBridge implements ItemGuardIntegration {
    private Method lookup;
    private Object api;

    public String name() { return "MyPlugin"; }

    public boolean isAvailable(PluginContext context) {
        Plugin p = context.plugin("MyPlugin");
        if (p == null || !p.isEnabled()) return false;
        try {
            this.api = Class.forName("com.example.api.Api", false,
                    p.getClass().getClassLoader())
                .getMethod("get").invoke(null);
            this.lookup = this.api.getClass()
                .getMethod("findAt", Location.class);
            return true;
        } catch (ReflectiveOperationException e) {
            context.logger().warning("MyPlugin API not found: " + e);
            return false;
        }
    }

    public boolean ownsBlock(Block block, Location location) {
        if (this.lookup == null) return false;
        try {
            return this.lookup.invoke(this.api, location) != null;
        } catch (ReflectiveOperationException e) {
            return false;
        }
    }
}

Community Addons

Submit an addon

Built a bridge? Open a submission issue and we'll review it. Once it's accepted, the JAR goes into the repo's addons/ folder and shows up on the Available addons page.

  1. Implement ItemGuardIntegration and register it under META-INF/services/.
  2. Build your JAR against itemguard-api with scope provided.
  3. Open a submission issue using the button below and fill in the fields.
  4. We review, test, and publish it if it checks out.
Submit your addon Report a bug Request a feature Ask in Discussions

Before you submit

  • Your name() is unique, lowercase and stable.
  • The API is a provided dependency — don't bundle it.
  • Source code is public and there's a direct download for the JAR and the source ZIP.
  • You've tested it on Paper 1.21+ (and Folia if you can).
