Translations

Every message the plugin shows to a player comes from a file you can edit. Nine languages ship on board, and each message documents the placeholders it accepts.

plugins/ItemGuard/translations/ · English is en.yml like the rest

Set lang: in config.yml to switch. Any value the plugin does not ship falls back to English with a warning in the console.

Why a folder of its own

On first start the folder translations/ is created with all nine files, and they are yours to edit: change the wording, the colours, add a line. They live in their own folder so they cannot be lost together with the database — a translation file sitting next to itemguard.db is one rm away from being deleted with it. English is en.yml like the rest, so all nine files sort together and none is special-cased by name.

How editing works

Your copy wins for every key it has. A key that a new version added — and that your file does not have yet — is read from the bundled file, so there is nothing to delete after an update, and no raw keys in chat. /ig reload re-reads them without a restart.

Upgraded from an older version? Files a previous version kept in the data folder root as messages.yml, messages-<code>.yml (or the hand-renamed messages_<code>.yml) are moved into translations/ under today's names on the first start after the upgrade, so your custom wording survives. A file that already exists in the folder always wins — nothing is overwritten.

Colour codes

Text supports & colour codes, hex colours as &#rrggbb, and named placeholders between braces, such as {id}, {player}, {amount} or {what}:

give:
  ok: "&aLlegó {player}: &f{amount} × {item} ({id})"   # comments in the file
                                       # document the placeholders a key accepts

Every key in en.yml documents in a comment which placeholders it accepts, so whoever edits the messages does not need to read the code.

One YAML trap

yes and no are booleans in YAML 1.1 So a key named after one of them makes the message come out as its own name. Rename the key rather than quoting the value — quoting works on the file you see, but the fallback read from the jar follows the same rule and would disagree.
