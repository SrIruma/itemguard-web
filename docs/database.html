Database

One database per server, by design. Your shop server, your faction server and your hub keep three separate copies of the guard — and the plugin enforces it, because it is the only way the data keeps its meaning.

SQLite out of the box · MySQL and PostgreSQL for a bigger disk, your own backups, or a second machine

SQLite by default

A single file at plugins/ItemGuard/itemguard.db, no database server, nothing leaves the machine. The right choice until you can say why not. Back it up with the same routine that backs up the world; like the world, it changes while the server runs, so back it up from a file-level snapshot rather than by copying a live file.

MySQL and PostgreSQL

database:
  type: postgresql     # sqlite | mysql | postgresql
  host: db.example.net
  port: 5432           # 0 uses the engine's default, 3306 or 5432
  name: itemguard
  user: itemguard
  password: ""
  params: "sslmode=require"   # TLS through a proxy, in the standard form
  • The JDBC drivers are inside the plugin jar — nothing else to install.
  • The tables are created on the first start; the account only needs rights on its own schema.
  • params carries the usual connection strings, e.g. sslmode=require or useSSL=true&requireSSL=true.
  • The password is never logged: the start-up line prints the URL with it masked, and a password= parameter you add by hand is redacted too.
A plain-text password sits in config.yml. Keep that file out of version control and out of screenshots.

One server per database, enforced

Each install keeps a server-id in its config.yml, generated on first start, and the database remembers the one that claimed it. A second server that points at the same database is refused on its first start, with a message naming the install that owns it.

Why enforce rather than document it: these tables are full of world names and coordinates, and a world name is not a coordinate until you know whose world it is. With two servers sharing one database, /ig find would report a chest that is not there, /ig tp would walk an admin over to the wrong place without complaining, and the seal sweep would lay bedrock under coordinates that mean something else — all silently. One database per server is the only way those three commands are allowed to say what they mean.

Running several servers, or moving one

  • Running several servers? Give each one its own schema on the same MySQL or PostgreSQL server (one CREATE DATABASE each) and each jar its own config.yml.
  • Moving a server to new hardware? Copy the whole plugins/ItemGuard folder — server-id included — and it carries on.
  • Editing the id by hand turns the install into a different server in the one way that matters, and its own database will say so on the next start-up.

The engine in use is printed on start-up and shown by /ig integrations.
