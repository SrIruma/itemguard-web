In-game screens

A player is told things on a screen, not in chat. Chat is scrolled past; a menu is read.

5 screens · 35 entries a page · nothing clickable out

Four commands open a screen for a player, and print for everyone else:

/ig info <id|hand>            # the record
/ig info <id> history       # the event list
/ig list items               # every tracked object
/ig list templates           # the catalogue
/ig flag <target>             # the flags, read-only

The console has no inventory to open, so it gets the text output instead. Nothing about the rules changes: a screen shows the same data the command would have printed, and it re-reads that data every time it is drawn.

The screens

ScreenOpened byWhat it is for
Items/ig list itemsEvery tracked object, one icon each, most recently seen first
Record/ig info <id>, or an icon on the items screenState, owner, template, coordinates, dates and id, all on one screen
HistoryThe history button on the recordThe last fifty events, newest first
FlagsThe flags button, or /ig flag <target>All seven flags: value, where the value came from, what each one does
Templates/ig list templatesThe store's catalogue; an icon opens that template's flags

The record screen

Three rows. The object itself in the middle of the top row, with the whole record on its tooltip. The facts people look up separately — owner, template, location, state, flags, history — as their own icons in the second row. And in the third row, what can be done to it.

The itemNothing. The record, on its tooltip: state, owner, template, created, where and when it was last seen, and the id

Spyglass, ender pearl, beacon, anvil, iron blockFind, tp, recover, regenerate, seal — only for a player who holds the matching permission

A button runs the command as the player who clicked it, so the permission check, the confirmation prompt and the message are the command's, and there is only one of each. A button a player has no permission for is not drawn at all rather than drawn and refused: a menu full of dead buttons is a menu nobody trusts.

Action buttons close the screen before running. A confirmation asked behind an open inventory is a question nobody sees, and a screen showing pre-action data is worse than no screen.

The seal button follows the item, not just the permission. A sealed object gets “take the seal off” and an unsealed one gets “put a seal on”. A lost object has nowhere to put a seal, so the button is greyed rather than offered.

Why the flags screen is read-only

Changing a flag is /ig flag <target> flag=value — a sentence with a value in it. A row of toggles would let one stray click decide how an item behaves, and an item that cannot be picked up would be the sort of bug nobody could trace back. So the screen shows the seven flags with their value, the layer that value came from, the default, and one sentence on what the flag does, and changing one stays a command.

The layout

The same on every screen, so learning one teaches all of them:

row 1   entries, close barrier in the top right corner
row 2
row 3
row 4
row 5   black
row 6   previous .......... page .......... next

Every slot a screen is not using is a black stained-glass pane. An empty slot in the middle of a table does not read as “end of the data”, it reads as a broken item — so the panes go in first and the content is written over them. The barrier is in the same corner on every screen, because it is the one position that is the same on a two-row detail screen and a six-row list.

Lists hold 35 entries a page. Where there is no previous page, the arrow is still there and greyed out rather than absent: a control that appears only sometimes is a control players have to look for.

Nothing can be taken out

Every icon in a screen is a display item, so every click in one is cancelled and a drag across one is refused. Clicks in the player's own inventory and in any other container are left exactly as they were — only a screen refuses. Actions run on the next tick, so opening another screen from a click never happens while the click is still being dispatched.

An item that is gone

A screen re-reads the record when it is drawn. If the item was recovered, deleted or regenerated while the screen was open, the next draw says so in chat and opens nothing, rather than showing a screen of dashes.
